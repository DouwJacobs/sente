# Notifications

Issues #29–#40 provide persistent personal messages, preferences, deterministic financial detectors, shared suppression, opt-in browser push and redacted administrator diagnostics. The existing Toast component remains transient request feedback. Financial alerts never change ledger records, acceptance, seen state or budgets.

## Producer and delivery contract

`notificationEvent` and the shared `App.notify` / `notifyTx` service live in `internal/app/notifications.go`. A producer supplies a recipient, stable type, severity, bounded title/message, source kind/ID, all contributing account IDs, a logical dedupe key, an immutable occurrence time and explicit dismissal policy. Producers calculate financial conditions separately using authoritative financial services. There is no browser/MCP API for arbitrary event creation.

Standalone evaluations call `notify`; producers inside an existing authorized financial write call `notifyTx` with that SQL transaction and the evaluation time. Never call `notify` from inside a write: it would acquire the same lock again. Event persistence, dependency records and delivery receipt commit together with the triggering financial change. The `notificationAdapter` boundary writes channel work within that transaction. The in-app adapter persists the message; `notification_push_delivery.go` queues opted-in per-device channel work in the same transaction. Network delivery runs outside SQL writes. A push-only message retains a permission-checked payload for its direct link, without entering the in-app inbox or badge. Provider-level acceptance uncertainty is documented below.

Types are `system`, `budget_threshold`, `budget_projection`, `budget_overspend`, `unusual_spending` and `recurring_payment`; severities are `info`, `warning`, `critical`. Titles are 1–120 Unicode characters, messages 1–1000 and keys 1–200; invalid UTF-8, blank values, NULs, unknown types/sources and future/zero occurrence times reject. Up to 1000 account dependencies are canonicalized and deduplicated before fingerprinting. System events must use source `system`, ID 0, and no financial dependencies. Internal producers must not place financial content in system messages. Budget alert types require a budget-period source; unusual-spending and recurring-payment types require an account or transaction source with explicit account dependencies; an account/transaction source must be covered by that scope.

Each recipient must currently be active. Every dependency must be visible and readable by that recipient, even if the recipient is an administrator. Budget events require household membership, an existing period and only household accounts. Private accounts are excluded from budget event scope. Producers must include every account that contributed to their message; the service does not calculate their financial result or infer omitted inputs.

## Retry and reset semantics

A receipt uniquely identifies recipient + type + SHA-256 of the logical key. Its event fingerprint binds all event fields and canonical account dependencies. Exact retries return the existing record (or ID 0 if its payload was retained only as a receipt). A different payload/occurrence/scope with the same key returns conflict; read/dismiss/eviction never resets the receipt. Keys are scoped per recipient/type; they must not combine distinct privacy scopes. No raw keys or payloads enter logs or public receipt responses.

Producers must keep the original occurrence time and payload for retries. A genuine new condition/crossing needs a new key, including its explicit reset/cycle identity; reusing a key to update an alert is invalid. The condition service adds durable per-recipient/type/privacy-scope cycles, consumed state and cooldowns. Exact event receipts remain immutable; detectors never retry a changed payload using a delivered key. Condition resets create a new occurrence key. Read/dismiss and retention eviction do not reset detector state.

Validation/authorization run before dedupe, so an exact retry cannot bypass revoked access. In-app failures roll back the payload, dependencies and receipt and can be retried. Events disabled in both channels return `disabled` without a receipt; standalone event retries can later become deliverable. Financial detectors consume a disabled crossing, so enabling a type does not replay old alert episodes. Already delivered records remain in the inbox when preferences are disabled. Both financial and system types default to enabled for the available in-app channel; critical severity does not bypass the user's preference. Push preferences default off and require both an enabled type and explicit device subscription. Channels are independent: disabling in-app does not disable an opted-in push type. New types must be registered explicitly; in-app defaults enabled and push defaults disabled. Critical severity bypasses neither preference.

## Browser APIs

All endpoints use existing cookie authentication, origin checks, CSRF for writes, JSON error conventions and `Cache-Control: no-store`. Inbox responses never expose recipients, account dependencies, dedupe/event hashes or delivery receipts. Source kind/ID are structured references, not arbitrary URLs, and are returned only after current permission checks. The notification centre navigates through existing authorized loaders and handles deletion or permission changes safely.

| Endpoint | Contract |
| --- | --- |
| `GET /api/notifications?page=0&page_size=20&state=unread` | Newest-first paged `items`, filtered `total`, `inbox_total`, `unread_count`, `page`, `page_size`. Optional state is `read` or `unread`; page size is 1–100. |
| `GET /api/notifications/unread-count` | Current accessible, undismissed, unexpired unread count. |
| `POST /api/notifications/{id}/read` | Idempotently marks one accessible inbox record read; returns `ok` and unread count. |
| `POST /api/notifications/read-all` | Marks only currently accessible inbox records read in one serialized write; returns unread count. |
| `POST /api/notifications/{id}/dismiss` | Hides a currently accessible record if its producer allowed dismissal. Unavailable, dismissed and non-dismissible records return 404. |
| `PUT /api/notifications/preferences/batch` | One to twelve distinct registered type/channel preferences in `items`; each requires explicit enabled/version. Saves all changes and their audits in one transaction, rejects the entire batch on stale versions or invalid entries, and returns the committed preference snapshot. `?channels=all` includes push; the default response retains the existing in-app-only shape. |
| `GET /api/notifications/preferences` | Registered in-app preferences, defaults and optimistic versions (0 for an unsaved default). `?channels=all` also returns push preferences, which default off. |
| `PUT /api/notifications/preferences` | Exactly one `type`, `channel: in_app` or `push`, explicit boolean `enabled`, and integer `version`; rejects stale versions, unknown fields/types/channels and omitted values. Returns current preferences. |

List/count share a SQL snapshot, and writes recheck the actor's session under the write lock. Each query applies recipient and privacy predicates before count/paging. Old messages disappear if a dependency becomes hidden/inaccessible/private (for budgets), the user loses household membership, or their source disappears or moves to an uncaptured account. Dependency account IDs deliberately retain tombstones instead of cascading away when an account disappears. Administrators cannot inspect another user's inbox. Permission restoration can make a still-retained record visible again. Read-all does not silently mark inaccessible messages read.

Offset paging is newest-first; additions can shift later pages, so the centre refreshes from page zero after mutations and periodic/focus refreshes. Counts reflect current permission and retention state, not the number of stored private/inaccessible payloads.

## Persistence, retention and lifecycle

Migration 24 appends notification receipts, payloads, account dependencies and preferences after baseline 23. It does not modify the frozen schema snapshot or existing financial/configuration/access rows. Fresh databases run 23 then 24; older fixtures upgrade through the same bridge. Failed schema or version-record writes roll back the whole pending batch.

Payloads expire from reads after 90 days, with a maximum of 500 stored payloads per recipient (including dismissed records). Eviction retains receipts. Receipts expire after 180 days; up to 5000 unexpired receipts per recipient are accepted, then new events return capacity error until cleanup releases space. This deliberately refuses further history rather than evicting recent idempotency evidence. Events whose occurrence is already at least 90 days old return `expired`, so a correctly retried old event cannot resurrect after its receipt expires. Clock time is UTC Unix seconds; producers need stable occurrence times.

Serving runs cleanup at startup and daily at Africa/Johannesburg midnight; delivery/state writes also clean expired records. Detector evaluations run at startup, at Africa/Johannesburg midnight for date-dependent conditions, and after committed source changes with a two-second coalescing window. Migration 27 adds transactional source revisions for transactions/allocations, category budgets/periods, categories and user/account access. Automatic and manual transaction imports, edits and MCP/configuration financial writes share those triggers; failed writes roll back revisions. Session writes and unrelated settings changes do not reevaluate detectors. Push jobs wake at their next due delivery/retry time independently; there is no minute polling. Failed evaluations or deadline queries retry after a minute. They use one current authorized SQL snapshot; multiple changes during that window are evaluated together. Offline commands do not evaluate or dispatch alerts. Logical expiry is checked at read time, independently of physical cleanup. Cleanup rolls back on failure and logs only a fixed diagnostic message; it retries on the next serving interval/activity. Shutdown waits for cleanup before closing SQLite. Offline commands do not start a scheduler. Soft user deletion immediately removes preferences, conditions, diagnostics, subscriptions, their outbox jobs, receipts and their dependent payload/scope rows while preserving financial history. Normal backups include notification state/preferences; restored sessions are invalidated through the existing restore behavior. Restored notification content still rechecks current permissions.

## MCP impact and remaining work

Notifications and preferences are browser-only personal communication workflows for now. Existing MCP connections have not consented to reading these potentially financial messages. No new tools, schema fields, allowlists, permissions, consent, proposal previews/audits or financial write semantics are added; no notifications are appended to MCP session context. A future MCP notification capability must require explicit consent and the same authorized service boundaries.

Implemented browser workflows (#31–#32): header bell with current unread count, paged All/Unread/Read inbox, explicit read/read-all/dismiss actions, authorized source navigation, and Settings notification preferences. Counts refresh every 30 seconds while visible, on focus and after personal state writes. Inbox snapshots are discarded while reloading; failed writes reload current accessible records. One Save changes action saves changed preferences atomically using optimistic versions; failed saves retain the draft and explicit Reload saved preferences discards drafts. Drafts survive Settings section changes. The same atomic Save changes action now covers both channels. Subscription permission is requested only by Enable this browser, never on page load.

## Financial detectors and suppression

Owner-approved defaults (8 October 2026): budget thresholds 75/90/100%; projections after seven elapsed calendar days and three distinct spending days, with at least 10% and R100 projected overrun; unusual spending requires five historical matching observations; recurrence requires four stable weekly/monthly payments. These deterministic rules are conservative heuristics, not forecasting guarantees. Per-type/channel eligibility is configurable in Settings; detector percentages/tolerances are maintained defaults, with no percentage editor in this batch.

Budget alerts evaluate the active Africa/Johannesburg period (latest start, then highest ID for overlaps). They reuse `categoryExpenseTotals` with the dashboard and its saved category targets, assigned-period rows, expense allocations and signed refunds. Transfer principal and private/hidden accounts are excluded. Payload dependencies include all visible household accounts contributing to that authorized snapshot, so permission/privacy changes invalidate old links and reset absent conditions. The logical budget scope is the household category/period per recipient; adding an empty account does not replay a still-active crossing. Group target edits continue to maintain the authoritative category targets through the existing services.

| Detector | Trigger and reset |
| --- | --- |
| Threshold | Positive limit and spend at or above 75/90/100%. Reset strictly below the percentage. A jump emits only the highest crossed percentage and consumes lower crossings. All already active percentages remain silent. |
| Actual overspend | Spend strictly greater than the saved limit, including a zero budget. Exactly 100% is not overspent. Reset at or below the limit. This is a separate alert type from the percentage message. |
| Projection | Current pace = expense spend through today × inclusive period days ÷ elapsed days, using integer arithmetic. Require seven days, three spending days, positive spend, remaining period time, actual spend at/below the limit, and projected excess of at least 10% and R100. Refunds/edits/limit changes or actual overspend resolve the condition. New crossings have a 24-hour cooldown. |
| Unusual spending | Most recent matching expense in the last seven days, at least R1,000, at least three times the median of five earlier payments on five distinct dates, and at least R500 above that median. History is the preceding 180 calendar days in the same currently accessible account/category/merchant; exact normalized description is the fallback when no merchant exists. Transfers and refund transactions are excluded; category allocations are summed per parent. One ongoing outlier episode produces one message; a normal/no-longer-recent latest payment resolves it. New episodes have a seven-day cooldown. |
| Recurring payment | Four stable outgoing payments in the same authorized account/category/merchant or exact normalized description, with typical amount at least R50 and each baseline amount within 80–120% of the median. Weekly gaps are 5–9 days; monthly payments must be in adjacent months with 21–38-day gaps. Compare a new payment (within seven days) to four prior stable payments: at least 20% and R50 amount change, or outside a 3-day weekly/7-day monthly date tolerance. Missing payments trigger after the expected date plus that tolerance, with a 35-day grace horizon to avoid resurrecting stale commitments. Monthly expected dates clamp to month end. A continuing changed/missed episode stays silent until resolved; new episodes have a seven-day cooldown. |

Re-evaluation reconciles edits, category changes, refunds, splits, reassignment, targets and access changes. Removed scopes reset without deleting old immutable receipts. A disabled financial occurrence is consumed and never backfilled on enable. A new cycle inside a cooldown is suppressed, then can deliver on a later evaluation if still triggered. First evaluation may emit a currently active qualifying condition. Conditions not evaluated for 180 days are removed; diagnostics do not retain financial baselines or normalized descriptions.

## Browser push

Push setup stores a persistent VAPID key pair in the protected application database, generated only after explicit setup. Include it in private integrity-checked backups; never publish the key/subscription tables. Each user may register up to ten devices, remove one independently, and send a rate-limited test (once per device per five minutes). Re-registration is idempotent for the same owner; another user cannot take over an endpoint. Enabling a browser resets a local subscription belonging to a different user before creating a new one. No type is silently enabled by subscription.

The channel outbox is unique per subscription/logical occurrence. Before claiming a send, the dispatcher rechecks active recipient, device, preference, current account/source access, dismissal and retention. Opt-in test messages need no financial source. The encrypted provider payload contains only generic Sente text, an opaque tag and a local message link. The worker independently fixes the visible title/body to generic text and permits only the known same-origin notification route. Push-only details load through an authenticated, recipient-scoped direct endpoint; opening a message does not mark it read. Read/dismiss remain explicit and use current permission checks.

Provider endpoints must be HTTPS browser push URLs from FCM, Mozilla, Apple or Windows notification services. Registration validates P-256/auth material. Transport rejects redirects, proxies and private/local resolved addresses, dialing the checked IP to prevent DNS rebinding. Provider bodies, endpoints, keys and raw errors never enter diagnostics/logs. 404/410 removes expired subscription secrets/jobs. Definitive 429/5xx rejections have at most three total attempts with minute backoff; other rejected responses finish with a fixed code. Transport ambiguity and interrupted `sending` jobs become `uncertain` and are not automatically resent. Provider acceptance cannot guarantee device display; worker tags coalesce the same occurrence without renotify. Jobs expire for sending after five minutes and are physically removed after seven days.

Supported environments need HTTPS (or a browser-approved local secure context), PushManager, ServiceWorker and Notification support; iOS may require a home-screen install. Unsupported/denied browsers retain in-app workflows. The shared root push/PWA worker caches only build-listed static assets and a generic reconnect page; application HTML/API/session/financial responses remain network-only. The PWA registers it without prompting for notification permission; device subscription remains explicit opt-in. The worker is served with no-store and push opt-in refuses an unrelated worker. Installability, identity and update behavior are described in PWA.md. Real device/provider delivery requires an owner-run check after HTTPS deployment.

## Administrator diagnostics

Settings → Notifications → Diagnostics and its API require a current administrator. Filters cover registered type, fixed lifecycle status, recipient user ID and a 1–14-day range; paging is bounded to 100 per page. Metadata is recipient ID/current username/type, hashed logical key, evaluation time, channel, fixed status and bounded error code. No notification title/message, description, account/source ID, baseline values, endpoint or key is returned. Ordinary users cannot inspect another user's diagnostics or inbox. Routine checks are omitted and unchanged in-app transitions are suppressed; storage retains 14 days and at most 10,000 rows globally. Condition fingerprints identify episodes/scopes; channel fingerprints identify immutable deliveries.

New diagnostics record meaningful alert transitions (delivered, disabled, coalesced, cooldown suppressed, resolved) and push delivery attempts (no device, pending, sent, permission revoked, expired, channel failure, uncertain). Initial negative checks and unchanged consumed conditions produce no records. Repeated identical in-app transitions are suppressed until the state changes. Existing deduplicated/no-longer-triggered records are preserved under normal retention, hidden by default, and available using explicit status filters. Detector failures log only a fixed message. Fixed reason codes distinguish insufficient history/projection observations, stale history, unstable recurrence, below-significance/below-threshold, at/below budget, period complete, actual over-budget and preference-disabled evaluations. No raw financial debug dump exists.

### Browser registration troubleshooting

A browser error such as `Registration failed - push service error` occurs while obtaining the browser push subscription, before a device can be saved in Sente. Check browser push-messaging settings and network access to its provider. Brave requires **Use Google services for push messaging** in Privacy and security ([Brave documentation](https://support.brave.app/hc/en-us/articles/360017989132-How-do-I-change-my-Privacy-Settings)). Restart after changing browser settings and retry Enable this browser. Sente cannot change those settings. The browser shows actionable recovery in the shared toast; failed subscription attempts never save a device and remain retryable.
